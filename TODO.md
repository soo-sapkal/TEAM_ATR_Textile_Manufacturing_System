# Loom Ledger — Outcome Tasks

## Current delivery state
The route families and primary interaction surfaces exist in the Next.js demo preview, with selected session-only commands backed by guarded state transitions. This is **not** a complete production ERP integration: auth, database/RLS/RPCs, and many financial/HR/admin commands are not connected. The client brief PDF, `part1.md`, and authoritative `part2.md` were not present. Section notes below preserve the original acceptance clauses and distinguish implemented demo flows from incomplete or blocked behavior.

## 1. Core shell, identity, and access
_Status: Demo sign-in/personas, permission-union navigation and action gates, separate buyer shell, route boundaries, search, notifications, floor mode, and reduced-motion interaction are implemented. Live authentication/session enforcement and security are not._
- Provide public `/` and `/login` pages; authenticated staff routes use a staff shell, while `/portal` is isolated in a buyer-only shell with no staff navigation or command palette. Permission unions—not role names—govern navigation and action access. Show a clear forbidden state, and route buyers/staff away from the wrong shell.
- Provide role-appropriate landing/navigation from permission keys for ADMIN, MANAGER, PLANNER, OPERATOR, STOREKEEPER, INSPECTOR, DISPATCH, HR, FINANCE, and BUYER. Hide unavailable navigation; show disabled-with-reason for expected but unavailable in-page actions.
- Provide responsive navigation, breadcrumbs using human-readable entity codes, global search/command palette, alerts, notifications, floor-mode and motion preferences, and keyboard-accessible scan entry. All controls must be labelled and keyboard operable.

## 2. Dashboard and cross-cutting operational status
_Status: Seeded dashboard, alerts, notification read state, and user-assigned My Work are implemented. Alert filters, independent remote-panel failure handling, configured live refresh, and full browser accessibility verification remain open._
- Provide `/dashboard` with permission-composed widgets for orders at risk, machines, output, inspection backlog, low stock, ready-to-dispatch orders, alerts, and shift output; each displayed number links to a relevant filtered page. A panel failure must not block unrelated panels.
- Provide `/alerts` with severity/kind/entity filters and deep links; alerts explain that they clear when the cause is fixed. Provide `/notifications` with unread state, entity links, mark-one-read, and mark-all-read.
- Provide `/my-work` for assigned operations with large state-appropriate actions and a clear empty state. Use live refresh only as configured; demo mode must not claim real-time factory synchronization.

## 3. Yarn inventory and receipts
_Status: Stock/batch surfaces, a validated session-only receipt command, and append-only movement events are implemented. FIFO reservation/issue workflows, owner/requester-safe adjustment approval, and recovery against a live backend remain incomplete._
- Provide `/inventory` with searchable yarn items and batch views. Show **on hand, reserved, available, and held** separately, always with units; available is the headline stock number. Show reorder warnings and batch navigation.
- Provide `/inventory/receive` as a floor-critical form with supplier, delivery reference, received date/time, repeatable yarn lines, unit-cost, damaged/held/accepted quantities, location, intended-order tag, notes, and live summary. Require `received = accepted + damaged + quarantined/held`; accepted is auto-filled from the remainder but can be overridden; disable posting until valid. Explain that intended-order tagging does not reserve yarn.
- A receipt mutation carries an idempotency key and displays pending state; successful demo result is labelled as demo-only and links created batch codes. Preserve draft recovery where implemented. Provide batch detail, FIFO reservations, adjustment requests/decisions, and a read-only append-only movement ledger. Own adjustment requests cannot be approved by the requester; prevent a stock adjustment preview below reserved stock.

## 4. Orders, materials, and order traceability
_Status: Order list/create/detail/tracker surfaces and finance-key visibility exist. Full order create/approve/cancel/edit persistence, stale-conflict behavior, and atomic material reservation are not connected; plan release is disabled._
- Provide `/orders` filters for all documented display statuses, search, due-date sorting, order progress, and flags for at-risk/material shortage/quality hold. Provide a draft order form with buyer, requested date, priority, currency, product lines, units, rates, inspection criteria, and review. Do not invent a confirmed order when the demo/backend has not confirmed it.
- Provide `/orders/[id]` with overview, material check, plans, rolls, dispatch, permission-gated money, event timeline, and tracker. Show current stage, display status, quality-hold overlay, due date, remaining quantity, and plain-language delay reasons on the command page. Show shortage requirements and unit-aware quantities. Confirm/cancel/close/edit actions follow documented states; cancellation is blocked when rolls were dispatched; non-draft edits and risky actions require a reason where specified.
- Material shortage blocks plan release. Only show override when the user has both `production.plan` and `orders.approve`; require a reason of at least five characters. Otherwise explain manager approval is needed. Release reserves FIFO batches; refresh on stale stock conflicts.

## 5. Plans, production, machines, and downtime
_Status: Board/List, operation console, stage-compatible demo machine assignment, guarded state/output commands, machine board/detail, downtime events, and shift summaries are implemented. Gantt is explicitly unavailable without schedule timestamps; verified plan creation/release, batch issue, BOM/yield, and production-to-roll linkage remain open._
- Provide `/production` stage lanes for Spinning, Weaving, and Dyeing, grouped by operation state; state changes use explicit buttons, never free drag. Show order/plan, machine, shift, progress, operator, due date, and filters; provide Board/List/Gantt views and idle-machine assignment shortcuts.
- Provide plan details and creation/release interactions. Enforce ordered stage selection, quantity not exceeding ordered quantity, yield bounds, one active plan per order line, and documented shortage rules. Display materials, outputs, yield, operations, and roll links.
- Provide `/production/operations/[id]` with legal Start/Pause/Resume/Complete/Cancel actions, status, target and recorded good/waste/reject quantities with units, previous-stage same-unit availability, output form, issue-yarn form restricted to reserved batches, append-only output history, materials, and downtime notes. Require at least one output to complete. On the last stage, rolls are required when good output is positive and their decimal-safe quantity sum must equal good quantity; on earlier stages, roll creation is unavailable. Output retries reuse an idempotency key.
- Provide `/machines` and `/machines/[id]` with stage/status filters, output and downtime summaries, and only legal next-state actions. RUNNING requires an in-progress operation. Entering BREAKDOWN requires a reason and creates downtime; one open downtime per machine. Provide downtime end and maintenance flows with time and cost fields; missing cost rate is displayed as “Missing”, not zero. Provide shift summary.

## 6. Quality, rework, rolls, and scanning
_Status: Queue/inspection/rework/defect/passport screens, append-only demo dispositions, local evidence preview, camera/manual scan, and opaque-token-only public fallback exist. Real evidence upload, signed-token lookup, and authoritative defect/genealogy rules are not connected; passport lineage is only as complete as the seeded event links._
- Provide `/quality` with Waiting, Re-check, Rework, On hold, Passed, and Rejected queues/counters; oldest waiting is clear and aged backlog is highlighted. Inspection is per roll, not bulk. A quick pass still confirms; re-check requires the full form.
- Provide `/quality/inspect/[code]` with roll genealogy context, previous inspection history, four result choices (PASS, REWORK, REJECT, QUARANTINE), required defects for REWORK/REJECT, required reason notes for REJECT/QUARANTINE, and pass location. Provide evidence-upload UX with type/size guidance, progress, preview, and replace/remove controls. Display success, then offer the next queued roll.
- Provide rework start/complete and defect analytics. Provide `/rolls` filters and `/rolls/[code]` passport with complete append-only roll events, order/operation/machine/shift/operators/yarn batches/supplier, quality defects/rework, movement, shipment, and invoice history. Only ACCEPTED rolls may be allocated; no roll split/merge UI. Provide scan camera UX with manual-code fallback and safe same-origin QR/token handling.

## 7. Dispatch and finished stock
_Status: Eligible-roll demo allocation, shipment creation/confirmation, idempotent confirmation, printable demo artifacts, and reconciled seeded load membership are implemented. Invoice/dispatch are demo-only; reversal/cancellation and the authoritative over-delivery transaction are not connected._
- Provide `/dispatch` views for ready orders, drafts, dispatched, cancelled/reversed; provide shipment creation and a load-the-truck detail view. Allocation lists only eligible ACCEPTED rolls belonging to the selected order and shows a decimal-safe allocated-versus-ordered meter and over-delivery tolerance.
- Show race/conflict errors and refresh eligibility rather than assuming availability. Confirm dispatch is retry-safe/idempotent and produces one invoice; the UI must not claim a real shipment in demo mode. Provide cancel/reverse where permission/state allows, finished-stock view, and print-only dispatch note/roll-tag views with browser-print styling.

## 8. Finance, HR, reports, and administration
_Status: Permission-gated overview/detail screens exist, but cost/payment/expense, attendance/payroll, reports/month close, integrity and admin write actions remain read-only/illustrative pending approved backend commands and separation-of-duties rules._
- Provide permission-gated finance summary, order cost breakdown, cost entries/reversals, buyer payments, and expenses. Every cost carries ACTUAL/ALLOCATED/ESTIMATED/MISSING basis; missing rates are never treated as zero. Validate outstanding balance/overpayment and append-only history.
- Provide attendance entry/approval/correction and payroll-period draft, calculation, approval, and labour-cost allocation. Enforce separation of duties and prevent changes to attendance inside an approved payroll period.
- Provide reports/month-close and integrity checks without implying statutory payroll/tax or predictive features, which are out of scope.
- Provide admin users/roles/permissions, master data, settings and audit views with permission gating, soft-deactivation presentation, and no destructive deletion of operational history.

## 9. Buyer portal and visual product system
_Status: Buyer-scoped demo portal and industrial design system are implemented. Layout rules, visible focus, semantic labels and reduced motion are present in source; no full WCAG audit or assisted-browser verification was run._
- Provide buyer-only `/portal` and `/portal/orders/[id]` surfaces limited to buyer-safe status, quantities, dispatches, and invoices; never expose rolls, machines, or order costs. Show the current stage and delivery progress in a clear Thread timeline.
- Use the Loom Ledger neo-brutalist industrial editorial design: cotton/ink/indigo/turmeric/madder/neem palette; Bricolage Grotesque, Public Sans, and JetBrains Mono; hard-edged slabs, selvedge accents, and the SVG Thread. Apply T0 floor, T1 office, and T2 showcase motion tiers; respect reduced motion and avoid obstructing task controls.
- Support 360/768/1280 layouts, visible focus, semantic landmarks, text-labelled statuses, 4.5:1 contrast, minimum 48 px floor touch targets, and complete loading/empty/error/stale states.

## 10. API adapter, demo mode, and domain-safe presentation
_Status: Decimal-safe schemas/helpers, typed envelope client, provisional endpoint/command map, query keys and guarded demo commands exist. The HTTP adapter is not activated; live endpoint shapes and DTOs require the absent source contract and server-side auth/RLS._
- Provide a typed HTTP/JSON client using the documented success/error envelope, request IDs, idempotency headers, decimal-string DTOs, query keys, and centralized error mapping. Keep proposed endpoint shapes in the adapter boundary and document that `Textile_Manufacturing_System.pdf`, `part1.md`, and `part2.md` were not attached.
- Provide deterministic demo data for 3 buyers, 5 yarn items (one below reorder), 12 machines (one BREAKDOWN and three IDLE), 4 orders (one at risk), 30 rolls across statuses, 2 shipments, and one payroll period, plus permission-edge scenarios. Clearly label the mock/demo mode and its non-persistent mutations.
- UI guards may prevent obvious invalid actions but the backend remains the business-rule judge. Never add/compare unlike units; never use JavaScript floats for money/quantity; never display UUIDs as human identifiers; never provide edit/delete controls for append-only movements, inspections, outputs, or costs.
